告别 Token：用 SSH Deploy Key 自动部署 Hexo 博客

发表于 2026-08-04 分类于 技术文章 ， CI-CD 阅读次数：

背景

这个博客的部署架构是典型的「双仓库」：源码在私有仓库 lixiandea/hexo_source_file（hexo 分支），推送到 GitHub Actions 后构建，再把 public/ 推到公开的 Pages 仓库 lixiandea/lixiandea.github.io（master 分支）上线。

这套架构里最麻烦的一点是：CI 要往另一个仓库推送，而 GitHub Actions 自带的 GITHUB_TOKEN 只能操作当前仓库，跨仓库推送必须额外携带凭据。之前工作流里用的是 personal_token（Personal Access Token），但实际从没成功过——目标仓库里全是 Site updated: 格式的提交（那是本地 hexo deploy 推的），没有任何一条 deploy: 提交。直到某次推送直接报 The process '/usr/bin/git' failed with exit code 128，才暴露了 DEPLOY_TOKEN 这个 secret 从未真正可用。

问题不是”要不要凭据”，而是”用什么凭据”。最后我选择了 SSH Deploy Key，这篇文章讲清楚为什么、怎么做、以及有什么风险。

为什么不用 PAT，而用 Deploy Key

跨仓库推送的凭据有两种主流选择：

维度 Personal Access Token SSH Deploy Key
权限范围 账号级，repo scope 等于所有仓库 只对指定仓库有效，且只授予 Contents 写权限
泄露影响 攻击者可读写你所有可见仓库 只能改写这一个 Pages 仓库
吊销方式 在 Developer settings 里逐个管理 在目标仓库 Deploy keys 里删掉即失效
是否经过账号体系 是，token 关联账号 否，纯密钥对，不依赖账号登录态
配置复杂度 需要登录网页创建、配 scope 本地生成密钥对，粘贴两次

PAT 最大的问题就是权限面过大：一个 repo scope 的 token 相当于把账号下所有仓库的读写权都交给了 CI。一旦这个 secret 泄露，攻击者拿到的不只是博客，而是你 GitHub 账号能看到的全部代码。Deploy Key 是一把”专钥专用”的钥匙：它只能推 lixiandea.github.io，就算泄露，损失也被锁死在这个仓库里。

另一个现实原因是它真的能跑通：Deploy Key 走 SSH 协议，不依赖 token 的 scope 配置、过期时间、SSO 授权这些环节，配好就是好的。

怎么做：完整步骤

1. 生成密钥对

生成两个文件：~/.ssh/blog_deploy_key（私钥）和 ~/.ssh/blog_deploy_key.pub（公钥）。

2. 公钥挂到目标仓库

打开 lixiandea.github.io → Settings → Deploy keys → Add deploy key：

  • Title 随便写，比如 github-actions-deploy；
  • Key 粘贴公钥内容；
  • 必须勾选 Allow write access，否则只能读不能推。

3. 私钥存为 Actions secret

打开 hexo_source_file → Settings → Secrets and variables → Actions → New repository secret：

  • Name：DEPLOY_KEY
  • Secret：私钥完整内容（含 -----BEGIN OPENSSH PRIVATE KEY----- 头尾），可以 cat ~/.ssh/blog_deploy_key 复制。

4. 修改 workflow

.github/workflows/main.yml 里把 personal_token 换成 deploy_key：

5. 验证

先确认密钥被 GitHub 认可：

返回 Hi lixiandea/lixiandea.github.io! You've successfully authenticated 就说明公钥挂载成功。然后随便推送一次（或重跑失败的 run），去 lixiandea.github.io 的提交页看有没有 deploy: ... 开头的提交——有就说明 CI 走通了。

6. 收尾

确认稳定后，把旧的 DEPLOY_TOKEN secret 删掉；本地私钥副本如果不再需要也删除，或移到 ~/.ssh/ 并 chmod 600 保管。

风险与注意事项

Deploy Key 方案不是银弹，几个点要心里有数：

1. 私钥泄露 = 博客仓库被改写

拿到私钥的人可以随意推送内容到 lixiandea.github.io，相当于能控制你博客的展示内容（包括挂恶意脚本）。所以：

  • 私钥绝不提交到 Git、dotfiles 仓库或任何公开位置；
  • 不要把私钥内容贴在聊天记录、工单里；
  • 本地副本用完即删，或放进 ~/.ssh 并收紧权限。

2. 一旦怀疑泄露，立即吊销

吊销 = 在 lixiandea.github.io 的 Deploy keys 里删掉这把公钥，然后重新生成密钥对、更新 DEPLOY_KEY secret。整个过程几分钟，比吊销 PAT 简单，这也是选它的加分项。

3. secret 存进去就看不到了

GitHub 的 secret 只能写入，不能回显。如果私钥丢了又没留本地副本，只能重新生成一遍，没有”导出”选项。

4. 一把 Deploy Key 只绑一个仓库

Deploy Key 不能跨仓库复用。如果以后还有别的 Pages 仓库，需要再生成一把新的。这是刻意的——权限最小化。

5. 每次 push 都会触发部署

工作流监听 hexo 分支，空提交也会触发（验证时我就是用空提交触发的）。调试 CI 时注意别制造无意义的提交；误推送后如果不想部署，只能等构建完再处理 Pages 仓库。

6. 构建在 GitHub 托管 runner 上执行

密钥会以 secret 形式注入 runner 环境，构建依赖（npm ci、克隆主题）也来自第三方。虽然 Deploy Key 权限被限制在单个仓库，但生产级 CI 仍建议固定 action 版本（目前是 @v4 标签），并留意依赖供应链变化。

总结

给”私密源码仓库 → 公开 Pages 仓库”的自动部署配凭据，原则就一句话：用最小权限的专钥，而不是账号级的 token。SSH Deploy Key 只对目标仓库有写权限、泄露可单点吊销、不经过账号体系，是这个场景下比 PAT 更可控的选择。配置成本只有”生成一次密钥、粘贴两次、改一行 workflow”，换来的是稳定可验证的自动部署和更小的爆炸半径。
